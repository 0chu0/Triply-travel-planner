## 一、总体架构设计

### 1.1 分层图（逻辑）

```
┌──────────────────────── 数据来源层 ────────────────────────┐
│ ① 手工 Golden Set（evals/datasets/*.json，入库版本化）      │
│ ② 生产会话采样（conversation/message 表 → 脱敏 → 人工标注） │
│ ③ LLM 合成（阶段 5，可选）                                  │
└───────────────────────────┬───────────────────────────────┘
                            ▼
┌──────────────────────── 执行层（Runner）────────────────────┐
│  case 加载 → 独立 thread_id / 独立 eval 用户 → 逐轮驱动      │
│  复用 create_travel_agent()（与生产同一入口，保证行为一致）  │
│  工具挡板（live / replay / stub）位于 middleware 工具注入层  │
└───────────────────────────┬───────────────────────────────┘
                            ▼
┌──────────────────────── 采集层（Collector）─────────────────┐
│  监听 astream_events v2：正文 / 工具调用 / token / 时延      │
│  结束时 aget_state() 读 current_step、user_requirement 等    │
│  产出「结构化 transcript」= 评测的唯一真相源                 │
└───────────────────────────┬───────────────────────────────┘
                            ▼
┌──────────────────────── 评分层（Metrics）───────────────────┐
│  A 确定性指标（规则，零成本、可复现）                        │
│  B LLM-as-Judge（rubric 多维打分，temperature=0）            │
│  C 人工标注（校准 judge 用，阶段 5）                         │
└───────────────────────────┬───────────────────────────────┘
                            ▼
┌──────────────────────── 存储与展示层 ───────────────────────┐
│  PostgreSQL 6 张新表（主存储，可 SQL 聚合、可跨版本对比）    │
│  CLI Markdown 报告（evals/reports/{run_id}.md）              │
│  管理 API（只读查询 + 小规模触发）                           │
│  前端 eval.html（阶段 5）                                    │
│  Langfuse：trace 关联 + 可选 score 双写（旁路，非主存储）    │
└─────────────────────────────────────────────────────────────┘
```

## 二、评测数据的来源与流转

### 2.1 数据集（Dataset / Case）的三种来源

| 来源 | 说明 | 规模建议 | 阶段 | 优劣 |
|---|---|---|---|---|
| **① 手工 Golden Set** | 覆盖 8 个步骤 + 边界场景，期望写死 | 12 → 30 条 | 阶段 0 | 可控、可判定；覆盖率有限 |
| **② 生产会话采样** | 从 `conversation`+`message` 筛选真实对话，脱敏后人工标注期望 | 20+ 条 | 阶段 5 | 最贴近真实分布；需人工标注成本 |
| **③ LLM 合成** | 用模型按场景模板批量生成用户话术 | 可选 | 阶段 5 | 量大；质量参差，需人工抽检 |

**推荐主线：① 起步 → ② 补充 → ③ 仅在需要压力测试时使用。**

### 2.2 Case 的结构（一条评测用例长什么样）

```
case = {
  id, dataset_id, title, category, tags[], enabled,

  # —— 输入：如何驱动 ——
  driver: "scripted" | "llm_simulated",     # 固定脚本 / LLM 扮演用户
  turns: [ "我想去西安玩3天", "预算3000左右", "带一个5岁小孩" ],
  max_turns: 6,

  # —— 期望：判什么 ——
  expected: {
    steps_path: ["requirement_collection","destination_recommendation"],  # 期望经过的关键步骤序列
    final_step: "destination_recommendation",
    tools_any_of: ["query_destination_info"],      # 期望至少调用到的工具
    tools_none_of: ["searchHotels"],               # 明确不该调用的工具
    requirement_fields: ["departure_city","travel_days"],  # 期望收齐的需求字段
    must_contain_any: ["天气"],                    # 正文应包含的关键词（任一）
    must_not_contain: ["帮你查车次","没有接入"],    # 禁用话术
    long_output_allowed: false                     # 是否豁免"≤8 行"约束
  },

  # —— 元数据 ——
  external_dependent: true,   # 是否强依赖外部 API（决定 stub 模式是否可跑）
  judge_enabled: true,
  weight: 1.0
}
```

### 2.3 执行与结果采集的流转（一次 Run 的完整生命周期）

```
1. 创建 run 记录（dataset_id、git_commit、model、prompt 版本、配置快照）→ status=running
2. 加载 enabled 的 cases（可按 tags / case_ids 过滤）
3. 对每个 case（受 Semaphore(concurrency) 限制）：
   3.1 thread_id = "eval-{run_id}-{case_id}"      ← 同时是 Langfuse 关联键
   3.2 user_id   = 配置的 EVAL_USER_ID（专用虚拟用户，隔离长期记忆）
   3.3 agent = create_travel_agent(overrides={...})   # temperature=0、工具挡板等
   3.4 for turn in case.turns:
         采集 = await collector.run_one_turn(agent, thread_id, turn, timeout)
         # 监听：on_chat_model_stream（仅主图 model 节点=正文）
         #       on_tool_start / on_tool_end（工具名、参数、返回摘要、是否报错）
         #       on_chat_model_end（token 用量）
       达到终止条件则 break
   3.5 state = await agent.aget_state(...)  → current_step、user_requirement 等
   3.6 transcript = { turns[], tool_calls[], final_answer, steps_path, token, latency }
   3.7 确定性指标 → 写 eval_case_result + eval_score(A 类)
   3.8 LLM judge（可关）→ 写 eval_score(B 类)
   3.9 异常/超时 → status=error|timeout，保留已采集部分，不中断整个 run
4. 聚合 → 写 eval_run.summary（各指标均值/通过率、分类切分、与基线 delta）
5. 清理（可配）：删除该 run 的 checkpoint 行、清理评测用户记忆命名空间
6. flush_langfuse()
7. status = success | partial | failed；产出 Markdown 报告
```

### 2.4 终止条件（多轮场景的关键）

按优先级：① 已走完 `case.turns`　② 到达 `expected.final_step`　③ 达到 `max_turns`　④ 单 case 超时（默认 180s）。
> 说明：本 Agent 是「模型主动调工具推进步骤」的形态，**不存在 interrupt/人工审批阻塞**（`approval_pending` 字段存在但当前 8 步流程未启用），因此不需要处理"等待人工确认"的挂起场景。若将来启用审批，需在此处补充 interrupt 处理。

## 三、评测指标定义与计算方法

分三类。**A 类是主力**（零成本、可复现、能进 CI），**B 类补主观质量**，**C 类校准 B 类**。

### 3.1 A 类：确定性指标（规则计算）

| 指标 key | 定义 | 计算方法 | 默认通过线 | 性质 |
|---|---|---|---|---|
| `answer_non_empty` | 是否产出正文 | 最终回答 strip 后非空 | =1 | 门禁 |
| `step_path_score` | 步骤路径是否按预期推进 | 期望序列为实际序列的**子序列**→1.0；否则 LCS(actual,expected)/len(expected) | ≥0.8 | 核心 |
| `final_step_match` | 终态步骤是否正确 | `current_step == expected.final_step` | =1 | 核心 |
| `tool_recall` | 该调的工具调了没 | \|期望∩实际\| / \|期望\|（期望为空则不计） | ≥0.5 | 核心 |
| `tool_precision` | 调的工具是否都是该调的 | \|期望∩实际\| / \|实际\| | 观察 | 观察 |
| `tool_error_rate` | 工具调用失败率 | 报错调用数 / 总调用数 | ≤0.2 | 观察 |
| `requirement_fill_rate` | 需求字段收齐率 | 已填字段数 / `expected.requirement_fields` 数 | ≥0.8 | 核心 |
| `format_clean` | 输出格式合规 | 无 `** / __ / ## / \` / 行首 * `，且正文行数 ≤8（豁免标记除外） | =1 | 门禁 |
| `forbidden_phrase_clean` | 禁用话术 | `must_not_contain` 全部未命中 | =1 | 门禁 |
| `must_contain_hit` | 关键内容覆盖 | `must_contain_any` 命中任一 | =1 | 核心 |
| `grounded_entity_rate` | 实体可溯源率（弱校验） | 从正文抽取「航班号/价格/温度」等实体，能在本次工具返回文本中找到的比例 | ≥0.8（informational） | 辅助 |
| `latency_ms` | 端到端耗时 | 首轮开始 → 末轮结束 | 观察 | 观察 |
| `total_tokens` | token 消耗 | `on_chat_model_end` 累计 | 观察 | 观察 |
| `turns_used` | 实际轮次数 | — | 观察 | 观察 |

> `grounded_entity_rate` 的**已知局限**：正文中的数字可能来自模型常识而非工具返回，误判为"未溯源"；也可能工具返回文本丢失导致误判。因此标定为 **informational（仅展示、不进门禁）**，真正的编造检测交给 B 类 `groundedness`。

### 3.2 B 类：LLM-as-Judge（rubric 多维打分）

| 维度 | 问的问题 | 权重（默认） |
|---|---|---|
| `requirement_coverage` | 关键信息是否收齐/回应到位 | 0.20 |
| `groundedness` | 是否基于工具返回的真实数据，有无编造航班号/价格/天气 | **0.30** |
| `instruction_adherence` | 是否遵守本步骤职责 + 全局输出规范 + 能力边界（不否认已接入能力、不承诺查车次） | 0.25 |
| `usefulness` | 建议是否具体、可执行、贴合用户约束（预算/带娃/天数） | 0.15 |
| `tone_naturalness` | 是否像真人顾问，不暴露内部（步骤名/工具名/字段名） | 0.10 |

- 每维 **1–5 整数分** + 一句中文 reason（≤30 字）
- `judge_overall = Σ(weight_i × score_i)`（0–5）
- **judge 输入**：case 标题与期望要点 + 完整 transcript（用户话术序列、工具调用摘要、最终回答）+ 当前步骤上下文
- **judge 输出**：严格 JSON `{scores:{...}, reasons:{...}, pass:bool}`，解析失败重试 2 次，仍失败记 `judge_error`（不影响 A 类结果入库）
- **稳定性控制**：`temperature=0`；关键 run 可设 `judge_repeat=3` 取**中位数**，同时记录 `judge_stddev` 作为元指标（>0.5 视为 judge 不稳，需查 rubric）

### 3.3 C 类：人工标注

`eval_score.metric_type = "human"`，与 judge 分并存不覆盖；用于计算 `judge_human_corr`（相关性/一致率），反向校准 rubric。阶段 5 落地。

### 3.4 Run 级聚合与回归判定

- 每个指标输出：`mean`、`p50`、`pass_rate`（有阈值的指标）
- 分类切分：按 `category` / `external_dependent` / `turns_used` 分桶
- **与基线对比**：`delta = target.mean − base.mean`
- **Gate（门禁）规则**：
  - `critical_fail`：任一**门禁指标**（`answer_non_empty`/`format_clean`/`forbidden_phrase_clean`）pass_rate < 95%
  - `regression`：`groundedness`、`step_path_score`、`tool_recall` 任一相对基线下降 > 5%
  - 触发任一 → run 状态 `failed`（用于"改 prompt 前跑一次、改后再跑一次"的回归判断）

## 四、结果存储与展示

### 4.1 数据表（6 张新表，全部继承 `Base`，`create_all` 自动建）

| 表 | 主键/关键字段 | 用途 |
|---|---|---|
| `eval_dataset` | id, name, version, description, is_active, created_by, created_at | 数据集（版本化） |
| `eval_case` | id, dataset_id(FK), title, category, tags(JSON), driver, turns(JSONB), expected(JSONB), external_dependent, judge_enabled, weight, enabled | 用例 |
| `eval_run` | id, dataset_id(FK), name, status, git_commit, model_name, prompt_version, judge_model, judge_prompt_version, config(JSONB), summary(JSONB), started_at, finished_at, created_by | 一次评测运行 |
| `eval_case_result` | id, run_id(FK), case_id(FK), status, final_answer(Text), steps_path(JSONB), tool_calls(JSONB), transcript(JSONB), latency_ms, prompt_tokens, completion_tokens, thread_id, error, created_at | 单用例执行结果 |
| `eval_score` | id, case_result_id(FK), metric_key, metric_type(deterministic/llm/human), value(Float), detail(JSONB), judge_model, judge_prompt_version, scored_at | 分数（一条一指标，易扩展） |
| `eval_baseline` | id, dataset_id, run_id, note, created_at | 标记基线 run |

> 说明：**不写入** `conversation`/`message`/`token_usage` 表 —— 评测不走 chat API，因此天然不污染用户数据、不消耗用户配额。

**为什么用「一条一指标」的 `eval_score` 而不是宽表？** 指标会持续增加（今天 14 个，以后可能有 25 个），宽表每次加指标都要改表；而 `create_all` 不会给旧表加列，改宽表等于要手写迁移。纵表避免这个问题。

### 4.2 展示方式（四种，按阶段交付）

| 方式 | 阶段 | 说明 |
|---|---|---|
| **CLI Markdown 报告** | 阶段 2 | `evals/reports/{run_id}.md`：总览表 + 分类切分 + 失败 case 明细 + 与基线 delta。**这是最主要的查看方式** |
| **管理 API JSON** | 阶段 4 | 供脚本/前端消费，支持分页与对比 |
| **前端 `eval.html`** | 阶段 5 | run 列表 → 详情（transcript 时间线 + 各指标分数 + judge reason）→ 失败 case 一键跳转 Langfuse trace |
| **Langfuse score 双写** | 阶段 4+（可选） | 把分数回写到对应 trace，在 Langfuse 里也能看到。**旁路，不作为主存储** |

### 5.2 需要修改的现有文件（最小改动清单）

## 六、与现有功能模块的集成点与潜在影响

| 集成点 | 关系 | 潜在影响 | 应对 |
|---|---|---|---|
| **Checkpointer（PG）** | 每个 case 建一个 `thread_id` | checkpoint 行膨胀（一次 30 case 的 run 会产生数百行） | run 后按 `thread_id LIKE 'eval-%'` 清理（可配开关） |
| **Store（长期记忆）** | Agent 会调 `update_travel_style_tool` 等写入 `user_id` 命名空间 | **污染评测用户记忆**，且污染会**跨 case 累积**导致结果漂移 | ① 固定专用 `EVAL_USER_ID`；② 评测模式默认禁用 MEMORY_TOOLS；③ run 后清理该命名空间 |
| **MCP 外部 API** | 评测会真实调用高德/Tavily/VariFlight/IGOHOTEL | **真实扣费 + 结果不可复现** | 三级挡板 live / replay / stub（见第七节对比 4） |
| **Langfuse** | 评测 trace 会混进生产项目 | 污染生产 trace 统计 | 主关联键用 `thread_id` 命名约定（`eval-{run_id}-{case_id}`），可精确过滤；tags 注入为可选增强（需实测 SDK 支持） |
| **Token 配额系统** | 评测不走 chat API | **不消耗** `token_usage`，也不受 402 拦截 | 需自行统计 run 的 token 成本（已设计在 summary 里） |
| **业务表** | 评测不写 `conversation`/`message` | 无污染 | — |
| **Prompt 版本** | `GLOBAL_OUTPUT_RULES` + 8 个步骤 prompt 会持续演进 | 不同时期的 run 不可比 | run 记录 `git_commit` + `prompt_version`，对比时提示"prompt 已变更" |
| **模型版本** | `QWEN_MODEL_NAME` 可切换 | 同上 | run 记录 `model_name` |

## 七、关键路径对比与推荐选择

### 对比 1：评测系统「托管形态」

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| **A. 全托管 Langfuse Datasets/Experiments** | 零自建存储；UI 现成；与 trace 天然一体 | 数据在 SaaS（网络依赖、免费额度、导出受限）；Dataset/Experiment API 在 langfuse 4.x 的具体形态**需实测确认**；自定义指标（步骤路径、格式合规）在平台侧表达困难；离线/CI 场景受限 | 不选 |
| **B. 自建：PG 存储 + 自建 Runner** ✅ | 数据主权；指标任意定制；可离线跑、可进 CI；与现有技术栈（FastAPI+SQLAlchemy）完全一致；无新增外部依赖 | 要写 ~1500 行代码；前端需自建 | **推荐（主线）** |
| **C. 混合：B 为主 + score 双写 Langfuse** | 兼顾：结构化数据在自家库，Langfuse 里也能看到分数与 trace | 多一处对接（需验证 SDK 的 score API） | **阶段 4 之后作为增强叠加** |

**推荐 B（后续叠加 C）的理由**：你的自定义指标（步骤路径、格式合规、禁用话术）恰恰是 Langfuse 平台**不擅长**的；而"改 prompt 前后对比"这个核心诉求，需要**长期可比的本地历史数据**，放在自家 PG 最稳。且你在面试时讲的是"自建评测流水线"，比"用了个 SaaS 功能"含金量高得多。

### 对比 2：评测「执行入口」

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| A. HTTP API 后台任务（FastAPI BackgroundTasks） | 前端一键触发，体验好 | 2C2G 机器上与线上服务抢资源；进程重启任务丢失；长任务难以观测 | 仅小规模 |
| **B. 独立 CLI 进程（`scripts/run_eval.py`）** ✅ | 资源隔离；可随时中断；易进 CI；输出直接落文件；崩溃不影响线上 | 需要 SSH/本地执行 | **推荐（主要方式）** |
| C. 作为 pytest 用例 | 与现有 tests 统一 | 评测耗时数十分钟、依赖外部 API、非确定性 —— **不适合放进单测**；会拖垮 CI | 不选（仅对 A 类纯函数指标写单测） |

### 对比 3：评测「粒度」

| 方案 | 说明 | 结论 |
|---|---|---|
| A. 组件级（RAG 召回率、rerank 效果） | 已有雏形（tests/test_advanced_rag.py） | 补充项，阶段 5 |
| **B. 会话/流程级（多轮跑完整流程）** ✅ | 与产品真实形态一致，能评"步骤推进、工具选择、越权、风格" | **推荐主线** |
| C. 单轮 prompt 级（对某一步 prompt 单独喂输入） | 快、省；但脱离了状态机与上下文，评不出"流程跑偏" | 不作为主线 |

### 对比 4：外部工具如何处理（**本项目最关键的技术难点**）

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| `live` | 最真实 | 真实扣费；结果不可复现（航班/酒店/天气随时变）；限流风险 | 小批量冒烟用 |
| **`replay`（录制回放）** ✅ | 首次真实调用后把输出存 fixture，后续按 `工具名 + 参数规范化 hash` 命中回放 → **可复现、零外部成本**；fixture 可人工审核 | 需要建 fixture 库；参数需规范化（日期等变化量） | **推荐默认** |
| `stub` | 完全断网可跑，最快 | 对依赖真实数据的 case 无意义 | 用于「纯流程 / 格式 / 边界话术」类 case |
| ❌ 在 `create_agent` 层替换工具 | 看似简单 | **会被 middleware 每轮 `override(tools=...)` 覆盖掉，无效** | **不可行**（已核实） |

**结论**：挡板必须实现在 **`StepConfigMiddleware` 的工具注入环节**（`request.override(tools=...)` 之前按名字替换），这是本项目特有的约束。

### 对比 5：多轮场景的「用户话术」来源

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| **固定脚本 `scripted`** ✅ | 确定性强、可复现、成本低、case 之间可比 | 覆盖不到用户的"意外回法" | **推荐主线** |
| LLM 扮演用户 `llm_simulated` | 覆盖面广、能探出鲁棒性问题 | 不稳定、成本高、结果不可复现 | 阶段 5 作为**探索性**补充（单独打标，不进门禁） |
| 生产回放 | 最真实 | 依赖历史数据质量 | 阶段 5（即数据集来源②） |

### 对比 6：Judge 模型选择

| 方案 | 结论 |
|---|---|
| 同 `qwen3.8-omni-flash`（temperature=0） | **默认推荐**：零新增成本、同一 provider；用细 rubric + 重复取样控制稳定性 |
| 更强/第三方模型 | 更准但增加一套密钥与计费；**配置为可选**（`EVAL_JUDGE_MODEL` 可覆盖），需要时再切 |
| 纯规则 + 人工 | 覆盖不到主观质量；作为补充而非替代 |

## 九、关键技术难点、风险点与应对

| # | 难点/风险 | 严重度 | 应对思路 |
|---|---|---|---|
| 1 | **外部 API 真实调用**：扣费、限流、结果不可复现 | 高 | 三级挡板（replay 为默认）；case 打 `external_dependent` 标；run 前估算调用量；设置 run 级预算上限（超阈值中止） |
| 2 | **middleware 每轮覆盖工具集**，工具替换/挡板无处下手 | 高 | 挡板实现在 `StepConfigMiddleware.override(tools=...)` **之前**；`create_agent` 层替换无效（已核实） |
| 3 | **非确定性**：生产 `temperature=0.7`，同 case 两次结果不同 | 高 | 评测强制 `temperature=0`（overrides）；报告中标注"评测温度与生产不同"；关键 case 提供 `pass@3` 稳定率 |
| 4 | **长期记忆污染**：记忆工具会写入 Store，且跨 case 累积 | 中高 | 专用 `EVAL_USER_ID` + 评测模式默认禁用 MEMORY_TOOLS + run 后清理命名空间 |
| 5 | **Checkpoint 数据膨胀** | 中 | `thread_id` 统一 `eval-` 前缀，run 后批量清理（可配） |
| 6 | **采集口径漂移**：评测采集的"正文"必须与生产一致，否则评的是另一套东西 | 高 | 抽出 `app/core/answer_stream.py` 供两边**共用同一判据**；阶段 1 验收明确要求"正文逐字一致" |
| 7 | **2C2G 资源争抢**：评测拖垮线上聊天 | 中高 | CLI 为主、默认并发 2；API 触发限并发 1 + 小规模；单 case 硬超时；提供 cancel |
| 8 | **judge 自评偏差**（同一个模型评自己） | 中 | rubric 具体到可判定（给出正反例）；重复取样取中位数；阶段 5 用人工标注算一致率校准；支持切换 `EVAL_JUDGE_MODEL` |
| 9 | **Langfuse trace 污染生产统计** | 低 | `thread_id` 前缀过滤；tags 双写为可选；必要时 `EVAL_LANGFUSE_TAG=false` |
| 10 | **Langfuse SDK 版本 API 不确定**（Dataset/Experiment/score 接口形态） | 中 | 阶段 4 先做**只读验证**：写一个探针脚本确认 4.15.2 的可用 API；不确定则跳过 score 双写，只保留 `thread_id` 关联（不影响主线） |
| 11 | **数据集维护成本**：期望写得含糊 → 指标不可判定 | 中 | 阶段 0 验收卡"期望可被无争议判定"；case 支持 `enabled` 软下线而非删除 |
| 12 | **磁盘**：checkpoint + transcript（JSONB）长期累积 | 低 | transcript 只保留最近 N 次 run（老 run 保留聚合 summary，清理明细）；沿用你已有的 `docker system df` 巡检 |

## 十一、实现后的「日常使用姿势」（闭环形态）

1. **改 prompt / 改工具 / 换模型前**：`python scripts/run_eval.py --dataset core_v1 --tag pre-change`（自动成为候选基线）
2. **改完后**：再跑一次 → `compare` 看 delta 与回归判定
3. **判定**：门禁通过 → 合入；`regression` → 看失败 case 详情 → 点 Langfuse trace 定位是模型、工具还是 prompt 的问题
4. **季度维护**：从生产采样 20 条新 case 补进数据集，重设基线

到这一步，README 里那句「评测未接入」就可以改成：
> **自建评测流水线**：30+ 条 Golden Case，14 项确定性指标 + 5 维 LLM-as-Judge，支持录制回放、基线对比与回归门禁；评测结果落 PostgreSQL，trace 与 Langfuse 双向可跳转。

## 十二、待你拍板的 3 个选项

| # | 问题 | 选项 A（推荐） | 选项 B |
|---|---|---|---|
| 1 | 评测主执行方式 | **CLI 为主 + API 小规模触发** | API 全量后台任务 |
